# Партиционирование в базах данных: стратегии и применение в банках

## 📊 Что такое партиционирование

**Партиционирование** — это физическое разделение одной большой логической таблицы на меньшие части (партиции) по определённому правилу, без изменения структуры таблицы для приложения. Это **внутренняя оптимизация СУБД**, в отличие от шардинга (разделение между серверами).

**Аналогия**: Если шардинг — это распределение книг по разным библиотекам, то партиционирование — это раскладка книг внутри одной библиотеки по разным залам (исторический, научный, художественный) для ускорения поиска.

### Сравнение с шардингом

| Критерий | **Партиционирование** | **Шардинг** |
| :--- | :--- | :--- |
| **Масштаб** | Один сервер, одна БД | Несколько серверов |
| **Цель** | Управление данными и производительность | Масштабирование и доступность |
| **Прозрачность** | Полностью прозрачно для приложения | Требует изменений в приложении |
| **Сложность** | Средняя | Высокая |

## 🗂️ Основные стратегии партиционирования

### 1. По диапазону (Range Partitioning)
```sql
-- Транзакции разбиваются по месяцам
CREATE TABLE transactions (
    id BIGSERIAL,
    client_id VARCHAR(20),
    amount DECIMAL(15,2),
    created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

-- Создание партиций
CREATE TABLE transactions_2024_01 PARTITION OF transactions
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE transactions_2024_02 PARTITION OF transactions
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
```

**Плюсы**: 
- Оптимизирует запросы по диапазону дат
- Легко архивировать старые данные (отключить старую партицию)

**Минусы**:
- Риск "горячей" партиции (например, текущий месяц)
- Сложность балансировки

**Для банка**: Идеально для **истории транзакций**, **аудиторских логов**, **выписок**.

### 2. По списку (List Partitioning)
```sql
-- Клиенты разделяются по типу
CREATE TABLE clients (
    id BIGSERIAL,
    name VARCHAR(100),
    client_type VARCHAR(20) NOT NULL -- 'INDIVIDUAL', 'BUSINESS', 'VIP'
) PARTITION BY LIST (client_type);

CREATE TABLE clients_individual PARTITION OF clients
    FOR VALUES IN ('INDIVIDUAL');
CREATE TABLE clients_vip PARTITION OF clients
    FOR VALUES IN ('VIP');
```

**Плюсы**: 
- Полный контроль над распределением
- Изоляция типов данных

**Минусы**:
- Ручное управление
- Дисбаланс при неравномерном распределении

**Для банка**: Подходит для **разделения клиентов по сегментам** (розничные, премиум, бизнес).

### 3. По хэшу (Hash Partitioning)
```sql
-- Равномерное распределение по client_id
CREATE TABLE account_transactions (
    id BIGSERIAL,
    client_id VARCHAR(20) NOT NULL,
    account_id VARCHAR(20),
    amount DECIMAL(15,2)
) PARTITION BY HASH (client_id);

-- Создание 4 партиций
CREATE TABLE account_transactions_p0 PARTITION OF account_transactions
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE account_transactions_p1 PARTITION OF account_transactions
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- и т.д.
```

**Плюсы**: 
- Максимально равномерное распределение
- Хорошо для балансировки нагрузки

**Минусы**:
- Невозможность целенаправленного запроса к партиции
- Сложно делать range-запросы

**Для банка**: Для больших таблиц с равномерным доступом — **очереди сообщений**, **кеширование сессий**.

### 4. Композитное (сочетание стратегий)
```sql
-- Сначала по дате, затем по типу клиента внутри месяца
CREATE TABLE operations (
    id BIGSERIAL,
    client_id VARCHAR(20),
    client_type VARCHAR(20),
    operation_date DATE,
    amount DECIMAL(15,2)
) PARTITION BY RANGE (operation_date, client_type);

CREATE TABLE operations_2024_01_vip PARTITION OF operations
    FOR VALUES FROM ('2024-01-01', 'VIP') TO ('2024-02-01', 'VIP');
```

**Применение**: Для очень больших и сложных таблиц, требующих многомерной оптимизации.

## 🏦 Практическое применение в банковских системах

### Сценарий 1: Оптимизация запросов к истории транзакций
```sql
-- Без партиционирования (медленно)
SELECT * FROM transactions 
WHERE client_id = 'CLIENT123' 
  AND created_at BETWEEN '2024-01-01' AND '2024-03-01';

-- С партиционированием по дате (PostgreSQL)
SELECT * FROM transactions 
WHERE client_id = 'CLIENT123' 
  AND created_at BETWEEN '2024-01-01' AND '2024-03-01';
-- СУБД автоматически обращается только к партициям:
-- transactions_2024_01, transactions_2024_02, transactions_2024_03
```

**Выгода**: Ускорение в 10-100 раз для временных запросов.

### Сценарий 2: Упрощение управления данными
```sql
-- Быстрое удаление старых данных (вместо DELETE)
DROP TABLE transactions_2022_01; -- Мгновенно

-- Быстрое добавление новых данных
CREATE TABLE transactions_2024_12 PARTITION OF transactions
    FOR VALUES FROM ('2024-12-01') TO ('2025-01-01');

-- Отключение партиции для архивации
ALTER TABLE transactions DETACH PARTITION transactions_2023_01;
-- Теперь можно сделать бэкап и убрать на холодное хранение
```

**Выгода**: Операции DDL вместо DML, минимизация блокировок.

### Сценарий 3: Изоляция критических данных
```sql
-- VIP клиенты в отдельной партиции с особыми настройками
CREATE TABLESPACE fast_ssd LOCATION '/ssd_storage/vip_data';
CREATE TABLE clients_vip PARTITION OF clients
    FOR VALUES IN ('VIP')
    TABLESPACE fast_ssd; -- Отдельное быстрое хранилище

-- Можно настроить отдельные индексы
CREATE INDEX idx_vip_phone ON clients_vip(phone) INCLUDE (name);
```

**Выгода**: Различные SLA для разных сегментов клиентов.

## ⚠️ Критические ограничения и подводные камни

1. **Неправильный ключ партиционирования**
   - **Проблема**: Частые запросы без ключа партиционирования → сканирование всех партиций.
   - **Решение**: Всегда включать ключ партиционирования в WHERE.

2. "Горячие" партиции (skewed data)
   - **Проблема**: 80% запросов к 20% партиций (например, текущий месяц).
   - **Решение**: Использовать хэш-партиционирование или субпартиционирование.

3. **Ограничения по внешним ключам**
   - **Проблема**: Не все СУБД поддерживают FK между партиционированными таблицами.
   - **Решение**: Проверять документацию (PostgreSQL 12+ поддерживает).

4. **Миграция существующих таблиц**
   ```sql
   -- НЕ делайте так на большой таблице (блокировка на часы)
   ALTER TABLE transactions ADD PARTITION BY RANGE (created_at);
   
   -- Делайте так (через новую таблицу)
   CREATE TABLE transactions_new (LIKE transactions) 
     PARTITION BY RANGE (created_at);
   INSERT INTO transactions_new SELECT * FROM transactions;
   ALTER TABLE transactions RENAME TO transactions_old;
   ALTER TABLE transactions_new RENAME TO transactions;
   ```

## 📈 Рекомендации для банковской разработки

### Когда использовать партиционирование
1. **Таблицы > 100 ГБ** с явным паттерном доступа (по дате, типу)
2. **Требования по хранению**: разные политики ретеншена для разных данных
3. **Частые запросы по диапазону**: выписки, отчёты за период
4. **Административные задачи**: быстрое удаление/архивация старых данных

### Когда НЕ использовать партиционирование
1. **Маленькие таблицы (< 10 ГБ)** — overhead превысит выгоду
2. **Отсутствие чёткого ключа** для партиционирования
3. **Частые запросы ко всей таблице** — партиционирование замедлит
4. **Сложные JOIN** между партиционированными таблицами

### Конкретные сценарии для банка
```sql
-- 1. Логи аудита (обязательное хранение N лет)
CREATE TABLE audit_log (
    id BIGSERIAL,
    user_id VARCHAR(20),
    action TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW()
) PARTITION BY RANGE (created_at);
-- Каждый месяц новая партиция, через 5 лет старые удаляются

-- 2. Кэш сессий (TTL по времени)
CREATE TABLE user_sessions (
    session_id UUID PRIMARY KEY,
    user_data JSONB,
    expires_at TIMESTAMPTZ
) PARTITION BY RANGE (expires_at);
-- Устаревшие сессии удаляются DROP PARTITION

-- 3. Очередь сообщений между сервисами
CREATE TABLE message_queue (
    id BIGSERIAL,
    service_from VARCHAR(50),
    service_to VARCHAR(50),
    payload JSONB,
    processed BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMPTZ DEFAULT NOW()
) PARTITION BY HASH (service_to);
-- Равномерная нагрузка на потребителей
```

## 🔄 Партиционирование как подготовка к шардингу

Партиционирование — это идеальный первый шаг перед шардингом:

1. **Прототипирование**: Отработать логику разделения данных на одном сервере
2. **Миграция**: Каждую партицию можно перенести на отдельный шард постепенно
3. **Гибридный подход**: Партиционирование внутри каждого шарда

```sql
-- Будущий шард: партиционирование + возможность миграции
CREATE TABLE transactions (
    tenant_id VARCHAR(10) NOT NULL, -- для шардинга
    created_at TIMESTAMPTZ NOT NULL, -- для партиционирования
    ...
) PARTITION BY RANGE (created_at);

-- Сегодня: все партиции на одном сервере
-- Завтра: партиции 2024 года -> шард1, 2025 года -> шард2
```

## 🎯 Заключение

**Партиционирование** — это мощный инструмент **управления жизненным циклом данных** и оптимизации производительности **в пределах одного сервера**. Для банковских систем это обязательная практика для:

1. **Соответствия регуляторным требованиям** по хранению данных
2. **Обеспечения производительности** критических отчетов и выписок
3. **Упрощения администрирования** больших объемов данных
