## Шпаргалка по выбору и настройке GC для High-Load Java (банковский контекст)

Ключевое правило: **выбор GC — это компромисс между пропускной способностью (throughput), задержками (latency) и используемой памятью**. В банковских high-load системах обычно критичны **низкие паузы (p99 < 10–50 мс)**, поэтому выбираем из G1, ZGC или Shenandoah.

---

### 1️⃣ Сравнение сборщиков мусора (GC) в таблице

| GC | Когда использовать | Типичные паузы | Потребление памяти (overhead) | Ключевая настройка |
|:---|:---|:---|:---|:---|
| **Serial GC** | Однопоточные приложения, мелкие heap (< 2 ГБ), Dev-стенды | Секунды | Минимальное | Не используется в проде |
| **Parallel GC** (Throughput) | Пакетная обработка, batch-задачи, где важна пропускная способность, а паузы не критичны (до 1–2 сек) | Секунды (но короткие) | Среднее | `-XX:MaxGCPauseMillis=<N>` (но не гарантирует) |
| **G1 GC** (Default с Java 9+) | **Универсальный выбор** для heap до 64 ГБ, баланс latency/throughput. Подходит для большинства микросервисов | 50–200 мс (настраиваемо) | 5–10% | `-XX:MaxGCPauseMillis=200` и `-XX:G1HeapRegionSize` |
| **ZGC** (Java 11+, 15+ production) | **Low-latency** для heap > 64 ГБ, паузы < 1 мс. Идеален для высоконагруженных API, реального времени | < 1 мс (субмиллисекундные) | 10–15% (дополнительная память для coloured pointers) | `-XX:+UseZGC` (управляет автоматически), настройки `-XX:ZCollectionInterval` и `-XX:ZAllocationSpikeTolerance` |
| **Shenandoah** (Java 12+, production) | Аналог ZGC, но с другим алгоритмом (evacuation). Хорош для больших heap и низких пауз | < 10 мс (обычно 1–5 мс) | ~10% (дополнительная память для forwarding pointers) | `-XX:+UseShenandoahGC`, `-XX:ShenandoahGCHeuristics` (adaptive/compact) |

---

### 2️⃣ Ключевые JVM-параметры для настройки GC

#### Для G1 (самый частый выбор)

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200               # цель по паузам (не жёсткая)
-XX:G1HeapRegionSize=16m               # размер региона (по умолчанию вычисляется)
-XX:InitiatingHeapOccupancyPercent=45  # порог запуска mixed GC (по умолчанию 45)
-XX:G1MixedGCLiveThresholdPercent=85   # процент живых объектов в регионе для mixed
-XX:G1NewSizePercent=5                 # размер young gen (5% heap)
-XX:G1MaxNewSizePercent=60             # max young gen
-XX:+ParallelRefProcEnabled            # ускоряет обработку ссылок
```

#### Для ZGC (низкие паузы)

```bash
-XX:+UseZGC
-XX:ZAllocationSpikeTolerance=2.0      # насколько агрессивно реагировать на всплески
-XX:ZCollectionInterval=120            # минимальный интервал между циклами (сек)
-XX:+UseLargePages                      # рекомендовано для ZGC (большие страницы памяти)
-XX:+AlwaysPreTouch                     # зарезервировать всю память при старте
```

#### Для Shenandoah

```bash
-XX:+UseShenandoahGC
-XX:ShenandoahGCHeuristics=adaptive    # adaptive / compact / passive
-XX:ShenandoahGarbageThreshold=25       # порог запуска сборки
-XX:ShenandoahUncommitDelay=5000        # задержка перед возвратом памяти ОС
```

### 3️⃣ Как выбрать GC в банковском high-load проекте?

| Сценарий | Рекомендуемый GC | Почему |
|----------|------------------|--------|
| **Микросервис с REST API, heap ≤ 32 ГБ, цель p99 < 100 мс** | **G1** | Баланс производительности и латентности, хорошо настраивается, зрелый. |
| **Стриминг / Kafka-консьюмер с heap > 32 ГБ, паузы критичны (< 10 мс)** | **ZGC** (или Shenandoah) | Субмиллисекундные паузы, не влияют на обработку сообщений. |
| **Batch-обработка (пересчёт процентов, ночные джобы), паузы не важны** | **Parallel GC** | Максимальная пропускная способность. |
| **Онлайн-API с требованиями < 1 мс (торговые системы, обработка платежей)** | **ZGC** | Единственный, кто даёт < 1 мс стабильно на больших heap. |
| **Если не знаешь, что выбрать — оставь G1** | G1 | Он дефолтный с Java 9 и работает хорошо в 80% случаев. |

---

### 4️⃣ Как мониторить и настраивать GC в проде

1. **Включи логи GC:**
   ```bash
   -Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=10,filesize=50M
   ```
2. **Смотри метрики:** паузы (p99, max), частота сборок, использование heap.
3. **Используй инструменты:** JMC, VisualVM, Grafana + Prometheus (сборка метрик через Micrometer).
4. **Тюнинг:** если паузы слишком большие:
   - Уменьши `MaxGCPauseMillis` для G1.
   - Для ZGC — включи `-XX:+UseLargePages` и проверь, что память не фрагментируется.
   - Для любого GC: увеличивай heap, если видишь частые Full GC.

---

### 🚀 Готовые рекомендации (шпаргалка для собеседования)

- **Если хост с памятью до 32 ГБ и p99 до 100 мс →** G1 с `MaxGCPauseMillis=200`.
- **Если память > 64 ГБ и нужны паузы < 10 мс →** ZGC (с `-XX:+UseZGC` и большими страницами).
- **Если считаешь, что нагрузка непредсказуема →** ZGC или Shenandoah (они лучше адаптируются к всплескам).
- **Не используй Serial GC в проде (только для отладки).**
- **Обязательно включи логи и мониторинг — без них настройка слепая.**

**Для банковского high-load:**  
«Мы используем G1 для большинства сервисов, а для критичных по задержкам (обработка платежей) перешли на ZGC. Настройка свелась к выбору `MaxGCPauseMillis` и отключению лишних фич (например, `-XX:-UseBiasedLocking` для ZGC). Логи GC идём в ELK, что позволяет быстро выявлять проблемы.»
