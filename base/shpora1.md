### 1. KAFKA: структура, топики, партиции, Consumer Group, отказоустойчивость

#### 🔹 Ключевые концепции (связка)

| Понятие | Суть | Как ответить |
|---------|------|--------------|
| **Топик** | Логический канал, очередь сообщений. | «Это как папка, в которую складываем события одного типа (например, транзакции).» |
| **Партиция** | Физическая единица хранения, часть топика. | «Топик разбит на партиции для параллелизма. Порядок сообщений гарантируется ТОЛЬКО внутри одной партиции.» |
| **Ключ (Key)** | Определяет, в какую партицию попадёт сообщение. | «Одинаковый ключ → всегда одна и та же партиция. Это основа для последовательной обработки одного счёта.» |
| **Consumer Group** | Группа потребителей, которые вместе читают топик. | «Каждая партиция читается только одним consumer'ом в группе. Если consumer'ов меньше, чем партиций, некоторые читают несколько.» |

#### 🔹 Как гарантировать последовательную обработку для одного счёта?

> «Я устанавливаю ключ сообщения = `accountId`. Все события одного счёта попадают в одну партицию, а внутри партиции Kafka гарантирует строгий порядок. На стороне Consumer Group я слежу, чтобы количество consumer'ов не превышало число партиций, иначе часть consumer'ов будет простаивать.»

#### 🔹 Отказоустойчивость Kafka

- **Репликация:** каждая партиция имеет leader + followers (реплики).
- **ISR (In-Sync Replicas):** список реплик, которые успели синхронизироваться.
- **acks:** 
  - `acks=0` — нет подтверждения (потеря данных).
  - `acks=1` — подтверждение от лидера.
  - `acks=all` — подтверждение от всех ISR (максимальная надёжность).
- **min.insync.replicas:** сколько реплик должны подтвердить запись.
- **При падении брокера:** ZooKeeper (или KRaft) выбирает нового лидера из ISR.

**Как ответить:**  
«В кластере Kafka отказоустойчивость строится на репликации партиций. Каждая партиция имеет лидера и реплики. При падении лидера контроллер (через ZooKeeper/KRaft) выбирает нового лидера из синхронизированных реплик (ISR). Для максимальной надёжности я настраиваю `acks=all` и `min.insync.replicas=2`, чтобы гарантировать, что сообщение записано как минимум на две реплики.»

### 2. ПАТТЕРНЫ МИКРОСЕРВИСОВ (MSA)

#### 🔹 Топ-3 паттерна, которые важно знать

| Паттерн | Суть | Когда применять |
|---------|------|-----------------|
| **API Gateway** | Единая точка входа для клиентов. | Маршрутизация, агрегация, аутентификация. |
| **Saga** | Управление распределёнными транзакциями через цепочку шагов и компенсаций. | Перевод между счетами в разных сервисах. |
| **Transaction Outbox** | Надёжная публикация событий в брокер. | Когда нужно гарантировать отправку события после сохранения в БД. |
| **Circuit Breaker** | Защита от каскадных отказов. | Вызов внешнего банковского шлюза. |
| **CQRS** | Разделение команд (запись) и запросов (чтение). | Отчёты, аналитика, fraud detection. |

#### 🔹 Как ответить на вопрос "Какие паттерны MSA вы использовали?"

> «В проекте мы использовали паттерны: API Gateway (единый вход и аутентификация), Transaction Outbox (для гарантированной отправки событий в Kafka после сохранения платежа) и Circuit Breaker (для защиты от сбоев внешнего банковского шлюза). Также применяли паттерн Saga для кросс-сервисных операций — например, при переводе между счетами в разных банках, где каждый шаг имеет компенсацию (откат).»

### 3. ТРЕЙСИНГ (DISTRIBUTED TRACING) — Jaeger / Zipkin

#### 🔹 Что такое распределённая трассировка?

> «Это инструмент для отслеживания пути запроса через несколько микросервисов. Каждый сервис создаёт спаны (span) — единицы работы (HTTP-запрос, вызов БД). Все спаны объединяются в один трейс (trace) по `traceId`, который передаётся в заголовках между сервисами. Jaeger визуализирует цепочку вызовов, показывает задержки и места ошибок.»

#### 🔹 Зачем нужен трейсинг в банке?

- **Поиск узких мест:** какой сервис тормозит перевод?
- **Аудит:** можно восстановить полный путь запроса.
- **Интеграция с логами:** `traceId` можно добавить в логи, чтобы фильтровать все логи одного запроса.

#### 🔹 Как ответить (шпаргалка)

> «В проекте мы использовали Jaeger для распределённой трассировки. Каждый микросервис (Payment, Account, Fraud) отправлял спаны в Jaeger. Это помогало нам быстро находить проблемные места: например, мы увидели, что банковский шлюз отвечает 900 мс, хотя ожидали 200 мс. Мы также внедрили Correlation ID, чтобы связать логи с трейсами — это сильно упростило расследование инцидентов.»

### 4. STREAM API

#### 🔹 Что спрашивают?

- **`map` vs `flatMap`**
- **`filter`**
- **`collect` / `groupingBy`**
- **`reduce`**
- **`peek`** (для отладки)

#### 🔹 Шпаргалка по map vs flatMap

| Операция | Что делает | Размер результата |
|----------|------------|-------------------|
| `map` | Преобразует 1 элемент → 1 элемент | Тот же размер |
| `flatMap` | Преобразует 1 элемент → 0..N элементов (Stream) и "сплющивает" | Может быть больше или меньше |

**Пример для запоминания:**

```java
// map: String → Integer
List<Integer> lengths = accounts.stream()
    .map(String::length)
    .collect(Collectors.toList());

// flatMap: Account → Stream<Transaction>
List<Transaction> allTxs = accounts.stream()
    .flatMap(acc -> acc.getTransactions().stream())
    .collect(Collectors.toList());
```

#### 🔹 `groupingBy` — группировка (важно для банковских задач)

```java
Map<String, BigDecimal> balances = transactions.stream()
    .filter(tx -> tx.date().isAfter(cutoff))
    .collect(Collectors.groupingBy(
        Transaction::accountId,
        Collectors.mapping(tx -> tx.type().equals("CREDIT") ? tx.amount() : tx.amount().negate(),
                           Collectors.reducing(BigDecimal.ZERO, BigDecimal::add))
    ));
```

### 5. JWT SIGNATURE

#### 🔹 Структура JWT

```
Header.Payload.Signature
```

- **Header:** алгоритм (HS256, RS256)
- **Payload:** данные (claims)
- **Signature:** подпись, которая подтверждает, что токен не был изменён.

#### 🔹 Как подписывается JWT?

**HS256 (симметричный):**
```
Signature = HMAC-SHA256(Header + "." + Payload, secretKey)
```
- Один секрет для подписи и проверки.
- Быстро, но секрет нужно безопасно хранить и распространять между сервисами.

**RS256 (асимметричный):**
```
Signature = RSA-SHA256(Header + "." + Payload, privateKey)
```
- Приватный ключ — на сервере, публичный — у всех.
- Безопаснее, т.к. сервисы проверяют токен по публичному ключу, не зная приватного.

#### 🔹 Как проверить JWT?

1. Вычислить подпись из `Header + "." + Payload` с тем же алгоритмом и ключом.
2. Сравнить с подписью из токена.
3. Проверить время жизни (`exp`).
4. Проверить `iss` (issuer), `aud` (audience), если нужно.

#### 🔹 Как ответить на собеседовании

> «JWT состоит из трёх частей: заголовок, полезная нагрузка и подпись. Подпись создаётся либо симметричным алгоритмом (HS256) — тогда один секрет для всего, либо асимметричным (RS256) — тогда приватным ключом подписываем, публичным проверяем. В банковских проектах я рекомендую RS256, потому что разные сервисы могут проверять токен без доступа к секретному ключу, что безопаснее. Подпись гарантирует целостность токена: любое изменение payload или header делает подпись невалидной.»

### КАК ОТВЕЧАТЬ НА ВОПРОС "ГДЕ ХРАНИТЬ JWT?" (если спросят)

> «Access token мы храним в памяти JavaScript (не в localStorage), чтобы защитить от XSS. Refresh token — в `httpOnly` cookie с Secure и SameSite=Strict, чтобы защитить от CSRF. Access token живёт 15 минут и обновляется через `/refresh`.»
